> 状态:**设计草案,暂不动代码**。目标是把 `out_pose2/` 的目录与 CSV 组织重新理顺,
> 让"切分 → 打标 → 聚类 → 用标签评估聚类"这条主线顺滑、可删、可对照、可复现。
> 本文逐条回应 7 个已提出的问题,再给出目标布局与分步路线。

> **代码基准:`compact` 分支(最新)**。下述现状均已对照 compact 核对:webapp 数据模型
> (`label_server.py`)、`segment.py`、`cluster_traj.py`、`export.py` 的读写路径与本文描述一致;

## 0. 现状数据模型(先把真值/派生关系画清楚)

理解一切问题的前提:**哪些是真值(source of truth),哪些是派生物(可随时重建)。**

```
真值 (truth)                          派生 (derived, 可删可重建)
─────────────────────────────        ──────────────────────────────
shards/{stem}/                        clips.csv        ← concat shards/*/clips.csv
  ├─ recording.csv  (1行 QC=完成标记)  segments.csv     ← concat shards/*/segments.csv
  ├─ segments.csv   (EMG burst)        recordings.csv   ← concat shards/*/recording.csv
  ├─ clips.csv      (pose 动作段)       clips_labeled.csv      ← export: clips ⋈ labels
  └─ overview.png                       clips_labeled/*.csv    ← 同上,按录音拆分
labels.csv  (打标日志, 逐clip)         cache/**               ← webapp 渲染缓存
invalid_recordings.csv (录音级失效)
```

- **打标真值** = `labels.csv`,主键 `(source_file, clip_id)`,webapp 每次打标全量重写(tmp+replace)。
- `clips.csv` 里的 `gesture_label` 列**永远是空的**,从不被填(真值在 `labels.csv`)。
- `clips_labeled.csv` / `clips_labeled/*.csv` 是 export 时 `clips ⋈ labels` 的**物化快照**,只含已标注、且剔除失效录音的行。
- 失效有**两个层级两套存储**:clip 级在 `labels.csv` 的 `invalid` 列;录音级在独立的 `invalid_recordings.csv`。
- webapp(`label_server.py`,compact)启动时把整张 `clips.csv` 读进内存建 `key→row` 索引。
- 另有 `recordings_keep.csv`:`pulse.sh raw-qc` 按 lag_flag / pose_nan_frac 阈值筛出的 QC 子集([pulse.sh:294-308](../pulse.sh#L294)),也是派生物。

> 一句话:`shards/` 和 `labels.csv` 是真值,**其它顶层 CSV 全是派生物,不该手编**。
> 现在的很多别扭,根因是"派生物被当真值在用/在改"。

## 1. 七个问题:现状 → 根因 → 方案

### 问题 1 · 网页从顶层 clips.csv 读数据,删除数据操作复杂

**现状**:webapp 读顶层 `clips.csv`(派生物)。想删某些数据时:
- 直接删 `clips.csv` 的行 → 下次 `rebuild_index` 又从 shard concat 回来,**删除不持久**;
- 真要删得去删 `shards/{stem}/` 整个目录 + 重建索引,webapp 还得重启重读 22 万行;
- webapp 本身**没有删除原语**,只有 soft `invalid` 标记(语义是"排除",不是"删除")。

**根因**:① 删除目标搞错了——应删真值(shard),不是派生物(clips.csv);② "永久删除"和"软排除"两个概念被混在一个 `invalid` 上;③ 索引是一坨大 CSV,不支持按行增删。

**方案**:
- 明确两类操作,各有归属:
  - **软排除(可恢复)**:打标动作,写进标注存储(见问题 2),不动 shard。下游查询默认过滤。
  - **永久删除(不可恢复)**:以 shard 为单位的一等操作 `drop_shard(stem)` —— 删 `shards/{stem}/` + 从索引里删对应行(增量,见问题 3),并记一条 tombstone 防止重切分时又被重新生成。
- webapp 暴露"删除该录音"按钮 → 调 `drop_shard`,而不是去编辑 clips.csv。
- 删除以**录音(shard)为最小粒度**;clip 级别只做软排除(单 clip 永久删除没意义,因为重切分会重新产生)。

---

### 问题 2 · 标注失效的数据另存一个 CSV,是否冗余?

**现状**:失效信息散在三处 —— `labels.csv` 的 `invalid` 列(clip 级)、`invalid_recordings.csv`(录音级独立文件)、`clips_labeled.csv`(export 时直接把失效行剔掉的物化结果)。

**判断**:**部分冗余,且割裂。** `invalid` 本质就是一种标注(取值为"废"),没必要单独开一个顶层小文件;录音级和 clip 级是两个 scope,但不该是两套机制两个文件。

**方案 —— 统一成一个"标注/排除"存储,带 scope:**

| 字段 | 说明 |
|---|---|
| `scope` | `clip` / `recording` |
| `source_file` | 录音 |
| `clip_id` | scope=clip 时有值;recording 时空 |
| `kind` | `label`(正常手势标签) / `invalid`(失效/废弃) |
| `value` | gesture 名(kind=label 时) |
| `labeler`, `labeled_at`, `note` | 元信息 |

- 这样 `invalid_recordings.csv` 并入统一存储(`scope=recording, kind=invalid`),**删掉这个独立文件**。
- `clips_labeled.csv` 仍可保留,但定位为**纯派生导出物**(见问题 5),不是失效信息的存储地。
- 好处:一处真值、一套主键、一套加载逻辑;问题 1 的"软排除"直接落这里。

### 问题 3 · 顶层文件每次从子文件夹合并,其实并不必要?

**现状**:`rebuild_index()`([segment.py:319](../segment.py#L319))每次全量 `glob shards/*/{clips,segments,recording}.csv` → concat → 覆盖三张顶层表。

**判断**:**"有一个索引"是必要的**(webapp/聚类要一张可查的全量表,临时打开 5310 个小 CSV 更慢);**但"每次全量重merge"不必要**。

**方案(两选一,按投入排序):**

- **A. 增量索引(改动小)**:索引仍是文件,但只对"新增/变更/删除的 shard"做增删行,而非整表重建。配合 commit point(`recording.csv` 的 mtime/存在性)判断哪些 shard 变了。
- **B. 换成单文件数据库 SQLite(改动大,但一次解决多题)**:把 clips / bursts / recordings / labels 作为表存进一个 `index.db`。
  - 删除 = `DELETE WHERE source_file=?`(解问题 1);
  - 打标 = `UPSERT`(解问题 2,标注就是一张表);
  - 查看/对照 = 一条 `JOIN`(解问题 5);
  - 评估 = `clusters JOIN labels`(解问题 7 的评估);
  - webapp 不必把 22 万行读进内存,按需查询。
  - shards/ 仍是真值;`index.db` 是**可从 shards 重建的派生物**(`rebuild --from-shards`)。

> 建议:短期先做 A(不阻塞当前打标);中期评估 B,因为它顺带把问题 1/2/5/7 的存储难点都解决了。
> **不变的原则**:顶层索引永远是派生物,真值始终在 `shards/` + 标注表。

### 问题 4 · burst 文件命名为 segment,不合理

**现状**:`segments.csv` 存的其实是 **EMG burst**(`start/end/hold_end/apex/emg_rms/envelope_peak`)。但 "segment" 这个词同时被用来泛指"要聚类的连续动作段",**一词多义,极易混淆**。

**方案 —— 改名,术语收敛:**

| 旧名 | 新名 | 含义 |
|---|---|---|
| `segments.csv` | `bursts.csv` (或 `emg_bursts.csv`) | EMG 激活段,辅助/对齐用 |
| `clips.csv` | `clips.csv`(不变) | **pose 连续动作段 = 聚类单元** |

- 同步改:`segment.py` 的 `SEG_FIELDS` / `rebuild_index` 映射、shard 内 `segments.csv`、以及读它的 `cluster.py`/`evaluate.py`/`export.py`(这些本就是历史代码,见问题 7,顺势一起改)。
- 术语统一后,文档/代码里 "segment" 一律指"连续动作段(=clip)",EMG 的叫 "burst",不再打架。

### 问题 5 · 打标结果不易查看 / 与原数据对照

**现状**:`labels.csv` 只有 `(source_file, clip_id, gesture_label, ...)`,**看不出这条 clip 是什么**(时长、动作区间、指标全在 `clips.csv`)。要对照得手动 join;`clips_labeled.csv` 虽是 join 好的快照,但**只在手动 export 时才更新、会过期**,且没有连到可视化。

**方案:**
- **总是新鲜的标注视图**:若走 SQLite(问题 3-B),直接建 `view_labeled = clips JOIN labels`,随查随新,无快照过期问题。若仍用 CSV,把"导出 `clips_labeled.csv`"做成打标后自动触发的增量更新。
- **一键对照原数据**:标注视图里每行带上该 clip 的渲染产物路径(`clips_export/{stem}/c{cid}.png` 关键帧 / `cache/mesh_cache_v3/...` 3D)。在 webapp 里点标签即可看动作回放;离线时 CSV 里有 png 路径可直接打开。
- **稳定 clip 锚点(关键,见下方"跨问题设计")**:让标注绑定到 clip 的采样区间而非易变的 `clip_id`,这样重切分后"对照"不会错位。

---

### 问题 6 · 聚类以连续段为单位;时序聚类 / 表征后聚类;结果位置要合理

**聚类单元**:`clips.csv` 的连续动作段(`motion_start_sample..motion_end_sample`,或整段 clip)的**关节角时序**。`bursts` 仅作对齐辅助,不是聚类单元。

**两条技术路线(并行试验,需要可对比):**
- **路线 A — 直接时序聚类**:对重采样到定长 L 的轨迹做 DTW / soft-DTW / k-Shape。
- **路线 B — 先表征后聚类**:autoencoder / 对比学习得 embedding → KMeans / HDBSCAN。

**两条路线的共同需求 —— 特征/表征缓存**:沿用现有 `traj_features/{stem}.*.npz` 思路,
按 `(stem, clip_id)` + **表征标签**(repr/L/model)做 key,换聚类算法不重算表征。

**聚类结果位置(收口,告别 out_raw/out_cmp 散落):**

```
out_pose2/cluster_runs/{run_id}/        run_id = 时间戳或参数哈希,可读
  ├─ params.json        # unit, repr, L, algo, k, group_by, 输入索引版本, ...
  ├─ clusters.csv       # source_file, clip_id, cluster_id   (与索引同主键, 可回join)
  ├─ metrics.json       # 内部指标 + 标签评估指标(见问题 7)
  └─ gallery/           # 每簇 medoid 关键帧 / 3D,便于人看
```

- 一个 run = 一个目录 + 一份 manifest,**参数自描述、不靠文件名后缀区分**。
- `clusters.csv` 主键与索引一致 → 评估时直接 `clusters ⋈ labels`。

### 问题 7 · evaluate / export 是历史代码,后续大改

**`evaluate.py` 现状**:只算**内部指标**(silhouette/contamination/leakage),输入 `segments_clustered.csv`,用 apex 特征 ——**完全不读人工标签**。
→ **重写为标签驱动的外部评估**:`cluster_runs/{run}/clusters.csv ⋈ labels.csv` on `(source_file, clip_id)`,输出 ARI / NMI / purity / 混淆矩阵 + 保留跨被试不变性指标;结果写回该 run 的 `metrics.json`。这才真正实现"打标结果评估聚类效果"。

**`export.py` 现状**:按"先聚类再给簇命名"的旧流程导出,读的 `labels.csv` 是 **`(group, cluster_id, label)` 的逐簇 schema** —— 与 webapp 写的**逐 clip** `labels.csv` **同名同默认路径但 schema 完全不同**。现在拿 export.py 指向 `out_pose2` 会直接 `KeyError`/导出 0 段。
→ **必须解决命名冲突**:webapp 的逐 clip 文件保留为权威 `labels.csv`;旧的逐簇文件随 export 重写一并废弃(若仍需"按簇导出",改名 `cluster_names.csv` 并明确语义)。export 重写为按 gesture 标签 / 按簇导出到干净布局。

→ 两者在新布局稳定前都标注为 **legacy / 待重写**,不再往上叠功能。

## 2. 跨问题的核心设计:稳定 clip 锚点

问题 1/5/6/7 都踩到同一个隐患:**标注主键 `clip_id` 是切分器在录音内分配的顺序号,不随重切分稳定。**
项目正处于"换切分引擎"阶段(切分规则仍在调,见 [docs/切分聚类问题与改进方向.md](切分聚类问题与改进方向.md)),
**每改一次切分,`clip_id=3` 可能指向不同动作,而 `labels.csv` 还引用旧号 → 标签静默错位。**

**方案:给标注绑一个对重切分稳健的锚。** 标注记录除 `(source_file, clip_id)` 外,额外存:
- `clip_start_sample, clip_end_sample`(打标当时的区间)
- `seg_version`(切分版本/参数哈希)

重切分后跑一个 `remap_labels` 步骤:用区间重叠把旧标签映射到新 clip,重叠不足的标记为"待复核"而非静默丢弃。
(若上 SQLite,这就是一张 `labels` 表加两列 + 一个 remap 脚本。)

## 3. 目标布局(汇总)

```
out_pose2/
├── shards/{stem}/                 ← 真值: 切分原子(不变)
│     ├─ recording.csv  bursts.csv  clips.csv  overview.png   (segments→bursts 改名)
├── annotations.csv (或 index.db 的 labels 表)   ← 真值: 统一标注/失效, 带 scope + 稳定锚
├── index.{csv|db}                 ← 派生: clips/bursts/recordings 全量索引(增量维护)
├── cluster_runs/{run_id}/         ← 聚类结果收口: params + clusters + metrics + gallery
│     ├─ params.json  clusters.csv  metrics.json  gallery/
├── features/ , traj_features/     ← 派生缓存: 按 (stem,clip_id,repr) keyed
├── clips_export/{stem}/c####.{npz,png}   ← 派生: 单 clip 切片 + 关键帧(对照用)

# 删除: invalid_recordings.csv(并入 annotations), clips_labeled.csv 降级为可选导出
```

**真值**:`shards/` + `annotations`。**其余皆派生,可一键重建。**

## 4. 分步路线(不破坏当前打标)

1. **改名 segments→bursts**(问题 4):低风险、纯术语,先做;同步改 segment.py 与读取方。
2. **统一标注存储**(问题 2):新 `annotations` schema(带 scope + 稳定锚),写迁移脚本把现有 `labels.csv` + `invalid_recordings.csv` 并进去;webapp 改读写这里。
3. **稳定 clip 锚点 + remap**(第 2 节):配合换引擎,保证标签不随重切分腐烂。
4. **增量索引 / SQLite**(问题 3):先增量化 `rebuild_index`;再评估上 `index.db`(顺带解 1/5)。
5. **删除原语**(问题 1):`drop_shard(stem)` + webapp 删除按钮 + tombstone。
6. **聚类 run 收口**(问题 6):`cluster_runs/{run_id}/` + manifest;迁移 cluster_traj 输出到此。
7. **重写 evaluate(标签驱动)+ export**(问题 7):基于 `cluster_runs` 与 `annotations`。

## 5. 需要你拍板的开放决策

1. **索引存储**:增量 CSV(改动小) vs SQLite(一次解决删除/打标/对照/评估,但要引依赖)。倾向 SQLite,但看你接受度。
2. **聚类单元**:确认是 clip 的连续动作段(`motion_*`)整段时序,而非 apex 静态向量?(早期实验 apex 静态曾胜出,这次是否彻底转向时序?)
3. **clips_labeled.csv 去留**:若上"总是新鲜的标注视图",这个物化快照是否还要保留为导出物?
4. **run_id 命名**:时间戳可读 vs 参数哈希可复现 —— 还是两者拼接(`{时间}__{参数哈希8位}`)?
